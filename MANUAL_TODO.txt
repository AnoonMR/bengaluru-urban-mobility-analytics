2. REAL HADOOP (your teacher asked specifically for Hadoop)
--------------------------------------------------------------------------------
Right now the MapReduce jobs run locally as real mapper -> shuffle/sort -> reducer
subprocess pipelines (pipeline/02_run_mapreduce.py) — this is the same execution
model Hadoop Streaming uses, and it satisfies the syllabus wording ("simulate or
implement MapReduce logic"). The mapper.py/reducer.py files themselves
(pipeline/mapreduce/job*/mapper.py, reducer.py) are written to be Hadoop-Streaming
compatible as-is.

Hadoop and WSL are NOT currently installed on this machine. If your teacher wants
to literally see `hadoop jar ...` run, or a screenshot of the Hadoop web UI, do
this yourself (this cannot be scripted for you — it needs a restart and admin
rights):

  a) Install WSL2 + Ubuntu (run as Administrator in PowerShell):
        wsl --install
     Restart Windows when prompted, then finish the Ubuntu setup (username/password).

  b) Inside the Ubuntu/WSL terminal, install Java + Hadoop (single-node,
     "pseudo-distributed" mode is enough for a class demo):
        sudo apt update && sudo apt install -y openjdk-11-jdk-headless
        wget https://downloads.apache.org/hadoop/common/hadoop-3.3.6/hadoop-3.3.6.tar.gz
        tar -xzf hadoop-3.3.6.tar.gz
        sudo mv hadoop-3.3.6 /usr/local/hadoop
     Then follow Apache's official pseudo-distributed setup guide to edit
     core-site.xml / hdfs-site.xml / mapred-site.xml / yarn-site.xml and format
     the namenode (`hdfs namenode -format`), then `start-dfs.sh` and `start-yarn.sh`.
     Full guide: https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/SingleCluster.html

  c) Copy this project into the WSL filesystem (Hadoop is much happier there than
     reading across the Windows/WSL boundary), e.g.:
        cp -r /mnt/c/all/3\ sem/bda/a2 ~/taxi-project

  d) Put the MapReduce input on HDFS and run Job 1 as an example
     (repeat -mapper/-reducer/-file for job2/job3/job4 the same way):
        hdfs dfs -mkdir -p /taxi
        hdfs dfs -put ~/taxi-project/outputs/mapreduce_input.tsv /taxi/

        hadoop jar /usr/local/hadoop/share/hadoop/tools/lib/hadoop-streaming-*.jar \
          -input /taxi/mapreduce_input.tsv \
          -output /taxi/out_job1 \
          -mapper mapper.py \
          -reducer reducer.py \
          -file ~/taxi-project/pipeline/mapreduce/job1_demand_by_hour/mapper.py \
          -file ~/taxi-project/pipeline/mapreduce/job1_demand_by_hour/reducer.py \
          -file ~/taxi-project/pipeline/schema.py

        hdfs dfs -cat /taxi/out_job1/part-00000 | head

  e) Take screenshots of the terminal output and of the YARN web UI
     (http://localhost:8088) — this is almost certainly what "screenshots" in the
     rubric wants, and it's the easiest way to visibly prove Hadoop was used.

If this feels like too much for the time you have, it is genuinely optional —
the pipeline/mapreduce scripts already demonstrate correct Mapper/Reducer logic
and the activity brief explicitly allows "simulate or implement". Mention in your
report that the jobs are Hadoop-Streaming-compatible and were also run locally

  fine for a class demo).

6. THINGS WORTH DOUBLE-CHECKING YOURSELF
--------------------------------------------------------------------------------
- I trained the models on a 300,000-row sample (trip duration) and the full
  191,546-row MapReduce Job 4 output (demand level) to keep training time
  reasonable on a laptop. If you want the duration model trained on the full
  722,432 rows, edit MAX_TRAINING_ROWS in pipeline/03_train_models.py and re-run
  `python pipeline\03_train_models.py` (takes longer, a few minutes).
- Demand-level thresholds (Low/Medium/High) are computed from the 33rd/66th
  percentile of trip counts per (date, hour, ~1.1km grid cell) — this is the same
  approach your friend's notebook used, just on a coarser location grid so the
  three classes actually come out balanced. Worth mentioning in your report.
